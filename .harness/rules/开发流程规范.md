# 开发流程规范

> SOP 阶段三 · Rules ③ | 需求到交付流程 + 提交/CR | 十阶段流程精简版

## 1. 流程总览(对接 SOP 十阶段)

```
需求 -> 分析(1) -> 需求评审(2) -> 编码(3) -> 编码评审(4)
    -> 测试(5) -> 测试评审(6) -> 推送(7) -> CI(8) -> 部署验证(9) -> 用户确认(10)
```

- 评审轮次:需求 ≤3 轮,编码/测试 ≤2 轮,超出升级人工
- 每阶段完成更新 `.harness/changes/{变更}/summary.md`
- 5 个 HITL 确认点:需求待决议 / 计划评审后 / 编码评审后 / 部署参数 / 最终交付
- 每个 skill 的加载见 `.harness/skills/README.md`

## 2. 分支策略

- **直接在 main 分支开发**,不开 feature 分支、不强制 worktree(项目约定)
- 质量由"推送前本地门禁"(§3)保证,而非分支隔离
- worktree 仅在并行开发多个独立需求时**可选**使用(见 `using-git-worktrees` skill)
- commit 粒度聚焦一件事;游戏接入一类一个 commit

> **调整说明(2026-07-11)**:原规则"禁止在 main 提交 + 必须 feature 分支"在单人开发中增加摩擦,且本项目 PR 阶段无强制 CI 门禁,分支隔离收益有限。经 laser-defense Dry Run 后改为 main 直接开发。**质量门禁不降级**:本地 validate+build 必过才 push main。

## 3. 推送前本地门禁(CI 不兜底,**必跑**)

远程 CI 仅跑 `validate-games`(且仅 games/scripts 变更时触发),lint/tsc/build 无保护:

```bash
npm run lint           # 必须 0 warning(--max-warnings 0)
npm run build          # tsc && vite build(含 sync-games + build:games:list)
npm run validate:games # 游戏元数据 + iframe 预检
```

三项全过(退出码 0 且产物存在且游戏数 > 0)才可 push main。详见 `unit-test-ci` skill。

> **教训**:无本地门禁则失败代码直接入 main 并触发部署;SOP "空跑误绿"风险。

## 4. 提交与 Code Review

- **直接 commit 到 main**:本地门禁(§3)通过后 commit,push main 触发 GitHub Actions(`validate-games.yml` 校验 + `deploy.yml` 部署)
- commit message:中文 + 类型前缀(`feat:`/`fix:`/`chore:`/`game:`)
- CR 标准(详见 `code-review` skill):
  - Critical(安全/构建失败/数据丢失)= 0 才可提交
  - Important 必须处理
  - Minor 记录待办
- CR 用 `requesting-code-review` 派发独立子代理,**不传会话历史**
- push 前用 `verification-before-completion` 精神:跑命令取证,非"应该过"
- 若需他人审查,可临时建分支开 PR;**默认 main 直接开发**

## 5. 游戏接入专项流程(主工作流)

local 游戏:
1. 建 `packages/games/{id}/`,加 `index.html` + 资源 + `metadata.json`
2. `npm run validate:games` 过 schema
3. `npm run sync-games` 同步到 `packages/app/public/games/`
4. `npm run build:games:list` 重建 games.json
5. 本地 `npm run dev` 验证可玩 + `npm run build` 通过

iframe 游戏:
1. 建 `packages/games/{id}/` + `metadata.json`(`iframe_url` 指向 `https://1games.io/...`,`aspectRatio` 推荐)
2. `npm run validate:games` 过嵌入预检(`can-embed.js`)
3. sync 自动生成响应式 wrapper 页
4. 本地验证 iframe 非空白 + 控制台无 X-Frame-Options/CSP 报错

> **教训**:"新增游戏：" commit 占多数,流程固定;漏 validate/sync 是常见失败点。

## 6. 提交规范

- message 风格(现有):中文 + 类型前缀,如 `feat: 新增游戏：xxx`、`fix: xxx`
- 单次提交聚焦一件事;游戏接入一类一个 commit
- AI 协作 commit 结尾加:`Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`
- 临时开 PR 时,body 结尾加:`🤖 Generated with [Claude Code](https://claude.com/claude-code)`
- 不提交:`node_modules/`、`dist/`、`.env`、`docs/`(被 gitignore)

## 7. 变更管理(对接 SOP 阶段九)

每个需求建 `.harness/changes/{类型}-{需求名}-{YYYYMMDD}/`:

```
summary.md              # 全流程追溯,每阶段更新
request_analysis/       # spec.md, tasks.md, review/
coding/                 # coding_report_vN.md, review/
unit_test/              # test_report.md, review/
ci_result/              # ci_result.md
deployment/             # deploy_report.md
```

- 评审文件版本递增(v1,v2...),**旧版本永不删除**
- `summary.md` 是 Single Source of Truth

## 8. 异常处理流程

- bug:先 `systematic-debugging` 找根因(4 阶段),再 `test-driven-development` 写复现测试修复
- CI 失败:回退编码/测试阶段,不猜
- 部署失败:回退 CI/编码,用 `deploy-verify` 逐项取证
- 3 次修复未果:停下质疑架构,找人讨论,不试第 4 次(`systematic-debugging` 红线)
